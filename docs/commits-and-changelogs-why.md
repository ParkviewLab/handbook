# Commits & changelogs: the reasoning, the evidence and the decisions

This file is the second half of the record of how release notes are generated. The line between the two is what a reader needs: [`commits-and-changelogs.md`](commits-and-changelogs.md) keeps every rule and every reason needed to apply one, and this file adds what is needed only to reopen a decision, which is the measurement the rule rests on, the alternatives set aside, and the dated rulings. Entries are in date order and the record at the foot summarises them. Dates are those of America/Los_Angeles, in which the rulings were dated, and a time, where one is stated, is UTC. The decisions were proposed on the organisation's wiki, in the book "One changelog generator"; what is needed to reopen them is recorded here.

It is a record, so it describes the past and keeps doing so ([`documentation.md`](documentation.md#documents-and-records)). An open question does not belong here; one about the changelog as it now stands goes to [`in-flight_ideas.md`](in-flight_ideas.md).

## 2026-09-17: the copied generator, measured

Until this change, each of eleven repositories carried a copy of the handbook's `templates/generate_changelog.py` and `templates/cliff.toml`. Its release workflow installed git-cliff, which built the list from the subjects of the commits in the release's range under the prefix policy that [`commits-and-changelogs.md`](commits-and-changelogs.md) then stated, and a model wrote the Highlights paragraph from the raw log. The copies had drifted into five versions of the script and three of the configuration. Every difference in the script was a licence header, added when a repository adopted REUSE, or drift: six copies lacked the `package.json` fallback the template had gained, all six in Python repositories, where it had no effect. The configurations differed by licence headers and by one improvement, pensa-grex's rule dropping the release job's own commit, which reached neither the template nor another copy. No difference needed to become an option of a shared script.

The measurement, made on 17 September 2026, ran the proposed rule, in an implementation of its own, over every release of the ten repositories that had released: pensa-grex, deco-assaying, smalt-mcp, ebony-enriching, conception-space, flint-slating, jonobones, paper-boxing, cobalt-grinding and cogrind-workshop. pensa-forma, the eleventh, had not released. A release was a tag matching `^v[0-9]+\.[0-9]+\.[0-9]+$`, 81 in all, 50 of them with a GitHub Release. The history came from full clones, the 231 merged pull requests from GitHub, and the published notes from each Release's body or, for a tag without one, from the tag's section of `CHANGELOG.md` on `main`. Four sets were compared in every release: the truth, the pull requests whose merge commit as GitHub records it lies in the release's range; the carriers, which the rule leaves out as carrying work recorded elsewhere; the expected set, the truth less the carriers; and the listed set. Everything was computed by script except the judgements on the Highlights paragraphs, which were the measurer's.

The rule listed exactly the expected pull requests in 79 of the 81 releases. The other two, conception-space v0.8.2 and v0.8.3, differ by intent: #11 and #12 were squash-merged into `develop`, and their squash commits were copied onto the release line for v0.8.2 minutes later without a trailer, so the rule lists both in v0.8.2, where they shipped, and not again in v0.8.3, where GitHub's commits for them first reach a release. It accounted for every one of the 601 commits in the 81 ranges: 202 were commits of listed pull requests, 64 branch commits absorbed into the real merges that contain them, 261 bookkeeping, 72 direct commits, and 2 the original squash commits of #11 and #12. Since the truth and the rule draw on the same record, GitHub's, their agreement shows chiefly that the rule, working from the commits, finds what that record says was merged. Four results stand apart from that circle. The rule departs from the truth where it should, at the two picks. The titles of the commits it classifies by content agree with the classification: all 112 recognised as version-only are titled as releases, openings of a development cycle, development builds or version bumps, and all 40 recognised as changelog-only are the release job's `docs(changelog): vX.Y.Z [skip ci]`. Every one of the 109 merges examined against its automatic merge equals it. And a synthetic history built with fixed dates, holding the cases the real history lacked, gave exactly the lists stated in advance; a second showed the cases the rule must report or could not see, among them a real merge picked commit by commit, which the rule as then written listed twice, as direct commits and again when the merge shipped (ruling 9b, below).

The published notes were recounted against the expected set. They omitted 122 pull requests by number, 5 of which were published only under the hash of a commit inside the pull request, and carried 34 lines that were no change of the release: 32 were the release job's own commit, which lands on `main` after the tag it documents and so was listed in the next release, and 2 were real changes made without a pull request. Every omission was accounted for. The written prefix policy dropped 77: the 34 whose titles carried `build`, `chore`, `ci` or `style`, and the 43 whose titles carried no recognised type. A first release's range was empty, because the copied script passed `..<tag>`, which git reads as `HEAD..<tag>`, empty whenever the checkout sits at the tag; that defect touched 61 pull requests and alone cost 42 of types the policy lists. The remaining 3 carried listed types but were merged for real at GitHub's default title, `Merge pull request #N from …`, a subject the policy dropped. git-cliff, re-run over every range with each repository's configuration as it stood at the tag, reproduced all 76 published lists exactly, so the omissions and the stray lines were properties of the generator, not of editing by hand; its rule `{ message = "^Merge", skip = true }` dropped nothing of its own, since `filter_unconventional` dropped every such subject in any case. The empty range was a defect; the prefix policy was written policy working as written.

The Highlights paragraph was the more complete of the two where the list had lost pull requests, but it is not a record of them: none of the 76 paragraphs cites a pull request's number. In eight releases whose lists had omitted pull requests, chosen with a weight towards the largest losses, the paragraphs described 49 of the 70 pull requests their lists omitted, 2 of them loosely in the measurer's judgement, and every one of 78 specific terms checked in them was found in the release's commit log, four only in other wording. The paragraph's input, the raw log capped at 50,000 characters, lost a pull request of its own: smalt-mcp v1.0.0's log was 55,580 characters long, and #16, beyond the cap, is the one pull request of that release its paragraph does not describe.

The organisation had no rulesets, so dev-tools' tags were protected by nothing, and six deletions of release tags were recorded across its repositories, most of them followed by re-creation at another commit, the latest pensa-grex v3.5.1 on 16 September 2026 after a failed release. Every recorded push was made by an account holding the organisation's administrator role. `main` was protected as [`ci.md`](ci.md#repo-merge-settings) prescribes only in the handbook and paper-boxing. dev-tools had no release workflow, although `ci.md` said it ran `release-txt.yml`, so its tags passed no gate.

The measurement's scripts and outputs are kept in dev-tools beside the acceptance run, in [`tests/acceptance/evidence/`](https://github.com/ParkviewLab/dev-tools/tree/main/tests/acceptance/evidence): `proposed_list2.py`, the rule as the measurement implemented it; `measure2.py` and the re-runs of git-cliff; `build_synthetic.py`, the synthetic histories with what was stated in advance for them; `evidence2.json`, every figure per release and per repository; and `measure.md`, the measurement's own report.

## 2026-09-17: the eighteen points the rule left open

The rule as first written was silent or ambiguous on eighteen points, which the measurement's implementation settled. The script follows that implementation on fourteen; the other four were put to decision 9 and ruled the next day, and two rulings of that day narrowed D8 and D6. The rule itself, seven rules with these points marked, is the docstring at the head of the script.

|---|---|---|

| D2, a first release | The whole history, `git rev-list <tag>` | As measured; `..<tag>` was the copied script's defect |
| D3, where GitHub's commits are looked for | Every ref of the clone, the release job's checkout fetching every branch and tag | As measured |
| D4, a squash commit | Committer `noreply@github.com`, one parent, the last `(#N)` of the first line | As measured |

| D6, cherry-picks | `git patch-id --stable`, a merge's over `git diff M^1 M`; the trailer tested first; a merge is never a pick; of several pull requests with one patch-id, the lowest number; no commit is a copy of one it precedes or descends from | As measured, the last clause ruled on 2026-09-18 |
| D7, carriers and picks | Carriers are left out of the patch-id index | As measured |

## 2026-09-18: one generator, in dev-tools

Built in [dev-tools #8](https://github.com/ParkviewLab/dev-tools/pull/8), with its tests, the acceptance run and dev-tools' release workflow. Released the same day as [dev-tools v1.2.0](https://github.com/ParkviewLab/dev-tools/releases/tag/v1.2.0), tag `v1.2.0` at commit 6337d27, published at 05:20 UTC on 2026-09-19, which carries #7 to #12: the script (#8), the licence of the Markdown under `tests/` (#9), the real-history set's relabelling (#10), the acceptance README's sentence on the tag ruleset and T7 as the set's source (#11), and the currency fixes made before the release (#12), besides #7, which removed the version guard's shallow re-fetch. The handbook's changelog part pins that commit.

Decision 1 was ruled (a): one script in dev-tools, `generate-changelog`, which every release workflow runs at a pinned release. It supersedes the copied `scripts/generate_changelog.py` and `cliff.toml`, the handbook's templates of both, and the step that installed git-cliff. The eleven copies had drifted into five versions, and the one improvement made in a copy had reached no other; one script at a pin has one content, and a repository that lags shows it as a version number, not as a silent difference.

Three alternatives were set aside. A corrected generator copied into each repository by a sync step, like the one that writes the pointer files, keeps eleven copies whose agreement depends on the sync being run in each after every change, which is the discipline that had not held. git-cliff kept, with the template corrected for a first release's range and for the release job's own commit, is the smallest change and cures the two faults, but it keeps a list built from commit subjects: it cannot name a pull request merged at GitHub's default title, recognise a cherry-pick, or tell bookkeeping by what it changes, and if pull requests were ever merged for real it would read every branch commit. The whole changelog job moved into dev-tools as a reusable workflow, called at the pin, would carry the job's text once; but each caller would still declare the job's permissions and pass the secret, the Electron repositories' installers would have to be downloaded and attached inside the called workflow, `ci.md` would need a rule for a workflow called across repositories, and the job's writes, the commit to `main` and the Release, would run from dev-tools' text. It was set aside rather than rejected: each copy of the job is compared with the template by the convention auditor and proven at its repository's next release; the northstar asks that dependencies between repositories be avoided, and a reusable workflow would widen this one from a script to the job that writes to `main`; and moving the job later needs no change to the script. If the copies of the job drift again, it is the remedy. The release-by-target change ruled the same day made the handbook's release templates into parts, so the job's text has one copy in the handbook, in the changelog part ([`releases-why.md`](releases-why.md)).

The cost accepted is a read of another repository on the release path, which the pin locks (decisions 7 and 8); a pin to move in each repository when the script changes; and permission to read pull requests. The northstar needed no amendment: its sentence that every pull request is squash-merged with a Conventional Commit title, "which is what the changelog is generated from", remains true, and so does axiom 1's "the changelog from commits", since every entry derives from a commit of the release's range and GitHub's record only describes the pull requests to which those commits belong.

Three points of the script's design carry reasons of their own. It is a Python script run under `uv run --script`, declaring the `anthropic` SDK at an exact version in its inline metadata, so the SDK's version is fixed in one place, where `uv run --with anthropic` in ten repositories' workflows and three templates had fixed it nowhere; it imports the SDK only inside the Highlights call, so its tests need the standard library alone. It takes the repository from `--repo`, never from its own location: the copied script took its root from its own path, which in a shared script would have read dev-tools' history and written into dev-tools' checkout. And it fails when it cannot read the pull requests, since a list built without them would be wrong without saying so, whereas the model's call alone degrades to a placeholder.

A dry run inside CI, by a manual dispatch added to each release workflow, was considered and set aside: it would add a second trigger and its conditions to every release template, and jonobones already uses its dispatch to publish an existing tag again. The dry run is made locally, from a dev-tools worktree at the pin, against each repository's own history.

## 2026-09-18: what the list holds

Decision 2 was ruled (a): Maintenance and Other changes are listed in full. This reverses the written policy that dropped titles of type `build`, `chore`, `ci` and `style`, to "stay in git history, not surfaced", and "silently dropped" any title without a recognised prefix, and it supersedes that policy and the dropped rows of the prefix tables. The policy caused 77 of the 122 omissions measured, and every one of the 77 was missing by number from the published notes, whether squash-merged or merged at GitHub's default title; a correct first-release range would have saved none of them, and a reader of the notes could not tell that anything had been dropped. What it dropped included real work: pensa-grex's rename (`chore: rename to PensaGrex`) and its Vite upgrade (`build: upgrade Vite toolchain …`), and deco-assaying #7, a Dependabot security update titled `Bump idna from 3.13 to 3.15 …`, dropped for having no prefix at all. Titles without a type included smalt-mcp's `C-1: multi-hop traverse …` and `C-9: reindex_page + reindex_all MCP tools`, which describe features. The cost is longer notes. Set aside were Other changes in full with Maintenance collapsed to one line counting its pull requests, their titles going to the job summary, and the policy kept.

Decision 3 was ruled (a): commits that reached a release without a pull request are listed under their own heading, Direct commits, after the groups, by subject and short hash. The 72 in the measured history include real changes, such as pensa-grex's rendering fix d8f9d8e with 108 lines of tests, which the copied tool had listed, so dropping such commits would have reintroduced the loss this change was made to end. A heading of their own tells the reader that these changes reached the release without review by pull request, which sorting them into the type groups would hide, and the sorting would rest on subjects that no check governs. Reporting them in the job summary alone was set aside as well. Whether every change to `develop` must arrive by pull request is a question of branch protection, and was left outside this decision.

Decision 4 was ruled (b): no title check for now, and a title without a type is listed under Other changes. The check first recommended, `pr-title`, a required check on every pull request into `develop` admitting exactly the eleven types the groups know, with an optional scope and `!`, would have grouped every later pull request by the type its author stated; 43 of the 202 listed pull requests had carried no recognised type. Its costs were that a pull request titled by GitHub's Revert button (`Revert "…"`) or by a Dependabot security update (`Bump x from a to b`) fails until it is retitled, that each repository gains one more required context, and that a pull request opened by a tool must carry a conforming title. The recommendation changed after decision 2 was ruled: with nothing dropped, the check would only group titles, at the cost of blocking those pull requests until retitled. The check remains idea A11 of [`handbook-improvements_ideas.md`](handbook-improvements_ideas.md), to be taken up if Other changes fills.

## 2026-09-18: the published notes stay as published

Decision 5 was ruled (c): nothing is regenerated. The notes are right from each repository's next release onward, and the published `CHANGELOG.md` files and Release bodies stay as published. The reason recorded with the ruling: the published notes stand as the record of what was released, and rewriting ten changelogs and fifty Release bodies, which keep no history when edited, costs more than correcting old releases is worth. What the published notes lack therefore stays lacking: 118 merged pull requests appear in them in no form, and 32 of their lines are the release job's own commit.

Set aside was the regeneration first recommended: the list under every section of `CHANGELOG.md` in the ten repositories and in each differing Release body replaced, in each repository once it had switched and only while no release of it was in progress, with every Highlights paragraph kept word for word, every Release body exported before its edit, since GitHub keeps no history of one, and no Release created for a tag that never had one. Regenerating `CHANGELOG.md` alone was set aside with it, as it would have left the two published forms of the same notes disagreeing for every tag that has both. The script's `--tag` accordingly serves a local run, a dry run and a repair, not a regeneration.

## 2026-09-18: the Highlights model

Decision 6 was ruled (a): the paragraph is written by `claude-opus-5`, pinned once in the script, where the copied script had pinned `claude-opus-4-7`. It is the current model of the tier already chosen, which Anthropic's model table prices as it priced the old pin. The choice was put for two reasons: the paragraph's input changed from the raw log to the list's entries, which changes the output whatever the model, so the output was to be checked once during the build in any case; and once the pin lives in one shared script, a model chosen later reaches a repository only through a dev-tools release and a pin moved. Keeping `claude-opus-4-7` would have spent that check on an older model; `claude-sonnet-5`, lower-priced, and `claude-fable-5-1`, priced above the Opus models, trade price against capability in opposite directions for a paragraph of four sentences, where neither trade is needed; and leaving the choice to the build would have left the ruling without the id on which it ruled.

The call was adjusted to the model. Adaptive thinking, the model's default, is left on and counts against the output limit, which the copied script had set at 600 tokens, so the limit was raised to 16,000 tokens, with the effort setting `high` that Anthropic's guidance for the model gave; the design had proposed a low one. The review of the script's pull request removed a server-side fallback on refusal (NR02), since the fallback would have written the paragraph with a model the script does not pin, against the ruling; a refusal gives the placeholder. The same review made a stop at the output limit give the placeholder (CR03), since under decision 5 a paragraph cut off mid-sentence would have stayed published.

## 2026-09-18: the pin, its policy and its lock

Decision 7 was ruled (b): a repository moves its pin during the next piece of work done in it, and no pull requests are opened across the repositories when dev-tools releases. The reason recorded with the ruling: eleven pull requests and merges for every change to the script would cost more than an idle repository running an older script for a while. The recommendation had been (a), a handbook pull request and one pull request in each adopting repository, opened the same day as every dev-tools release that changes the script, which ends drift of content and lets a repository lag only whilst its pin pull request is open, at eleven small pull requests per change. The cost accepted with (b) is drift of pins: an idle repository runs an older script, and a correction reaches it only with a later piece of work there. One organisation Actions variable holding the tag was set aside, since a change would reach every repository at once with no pull request in any, and a re-run of a past release job would read the variable's new value; so was a composite action whose updates an automated dependency tool would propose, since no repository runs one.

Two rulings on the build's open points, the same day, fixed how (b) works. A pin moves to the newest dev-tools release whose own release run passed, and the convention auditor checks each pin against that release; the recommendation had been the released templates' pin, and under the ruling the templates' pin catches up with the next handbook change. The ruling extends to the pin of the back-merge check proposed with real merges, whilst the documentation site's tag pin is separate and moves on its own occasions. And preparing a release counts as a piece of work: the release preflight reports a pin lagging behind the newest passing release, and a pull request moves it before the promotion. The reason given: a release is when the script writes the notes, and under decision 5 notes written by a defective script would stay wrong. The cost is one pull request, its CI and one merge before each release whose pin lags.

Late on 2026-09-18 the first of these rulings was refined, on reconsidering it before this file recorded its reason. As first ruled, a pin had to equal the newest dev-tools release whose own release run passed, so that with the second ruling every dev-tools release, one that leaves the changelog script unchanged included (a change to `git bump`, or the back-merge check proposed with real merges), would have made every repository's pin lag and cost each repository a pull request, its CI and a merge before its next release. Ruled: a pin names a dev-tools release whose own release run passed and which is at or after the floor, the newest such release that changed the pinned script. The convention auditor and the release preflight compute the floor from the releases whose range touched the script's file, and report a pin below it; the back-merge check's pin falls under the same rule with its own script. This supersedes the first ruling's requirement that a pin equal the newest passing release, whilst the target of a move is unchanged: a pin that is moved, or set for the first time, takes the newest release whose run passed. The reason recorded with the ruling: "A fix to the script reaches each repository at its next piece of work, without waiting for a handbook release; a dev-tools release that leaves the script unchanged makes no pin lag, so no repository pays a pull request for it; and only a release whose run passed is used, because a tag whose run failed can no longer be deleted and must be passed over."

Decision 8 was ruled (c): each changelog job pins dev-tools by the full commit SHA of the release, with the tag in a comment on the same line; dev-tools gains a ruleset on tags matching `refs/tags/v*` that restricts updates and deletions, blocks force pushes and names no bypass actor; and dev-tools' `main` is protected as `ci.md` prescribes. dev-tools also adopted `release-txt.yml`, as `ci.md` had said it ran, so each of its release tags is checked by the three-check gate (dev-tools #8).

A pin that can be redirected lets the code every pinned release job runs, with write access to `main` and to the Releases, change without a pull request anywhere, and lets a re-run of a past release job run code other than the original's. The two locks cover different cases. The ruleset refuses a tag's move or deletion while it is active, which stops the recorded pattern of a release tag deleted and pushed again at another commit; but GitHub documents that a ruleset can be set to Disabled, which stops its enforcement, or deleted, and an administrator of dev-tools can do either, so it guards against a re-tag made in the course of work and is not a lock. A pin by SHA names one commit by construction, and nothing done in dev-tools can redirect it; GitHub's documentation calls the commit SHA the safest reference for a called workflow, for stability and security, and idea A1 of the improvements notebook proposes the same form for third-party actions. The SHA alone would have left the tag in each comment, and the documentation site's tag pin, free to move; the ruleset alone suffices only if a guard against the recorded re-tags is judged enough, though it keeps each pin one readable value; and with neither, the tag's stability rests on convention. The cost of both is a second value in each pin, written by the pull request that moves it (`git rev-parse vX.Y.Z^{commit}`) and checked by the convention auditor against its tag, and the ruleset's own cost: a dev-tools release cut in error cannot be re-tagged, and is corrected by the next patch release. The gate of `release-txt.yml` runs on the push of a tag, after the tag exists, so it reports a bad tag but cannot prevent it; under the ruleset such a tag stays, and no pin moves to it. Protecting `main` matters because dev-tools' releases are cut from it.

The northstar asks that dependencies between repositories be avoided. Where that meets one shape across many repositories, its answer is shared sources, dev-tools among them, and `ci.md` admits a dev-tools script into a workflow only at an exact release, a locked dependency rather than one on dev-tools' state. The changelog job stays within that rule on one condition, that what the pin names cannot change, which a SHA meets by construction and a tag meets only while nothing moves it.

That no actor passes a ruleset with an empty bypass list was inferred from GitHub's documentation, which lets only actors with bypass permission past its rules, so the build was to try it on a scratch repository before the ruleset was applied anywhere (below).

## 2026-09-18: four points of the rule, and the narrowing of D8 and D6

9a was ruled (a): a carrier is recognised by its head branch alone, `develop`, `main` or `back-merge-vX.Y.Z`, and only for a pull request from the repository itself, not a fork. The measured clause that also counted any pull request whose base branch is `main` misfiled cogrind-workshop #1, a real change from `ci-node24-action-pins` into `main`, as a carrier and its commit 958c3f5 as a direct commit; every other carrier in the history has head `develop` or `main`. The fork condition was added because a fork's pull request may come from a branch that happens to be called `main`; it was specified and tested, not measured, since the measurement did not record the repository each pull request came from. It is the one ruling that changes a measured list: cogrind-workshop v0.1.0 lists #1 under Maintenance.

9b was ruled (a): a pull request merged for real and then picked onto the release line commit by commit counts as already shipped once each of its own commits has a patch-id among the commits reachable from the previous tag, so it is not listed a second time when its merge ships. As measured, the picks were listed as direct commits and the pull request again when its merge shipped. The rule was specified and tested on constructed histories, since no such pick occurs in the real history, and with it, merging pull requests for real would need no change to the script. A pull request picked as one commit with `git cherry-pick -m 1` is recognised under either ruling; whether the handbook should prescribe that practice was left to the proposal for real merges.

The review of the script's pull request found that D8, as 9b ruled it, and D6 took commits for copies that could not be copies (CR01, CR02). Ruled on 2026-09-18: a patch-id match counts as already shipped only when the earlier commit could be a copy of the later one. For D8, the matching commit is not the own commit's ancestor; for D6, a copy cannot precede what it copies. Before the narrowing, a pull request that re-applied a change which had shipped and been reverted was left out of the release that brings the change back, and nothing in the notes showed it; it is now listed there. Every pick onto the release line stays as ruled, and no measured list changes. The ruling required the narrowing before any repository merges pull requests for real; it was made in the script in dev-tools #8, and it supersedes D8 as first ruled under 9b.

The narrowing was extended to direct commits the same day: a commit counts as a copy of a GitHub-made commit only when that commit is not its ancestor, on both the trailer and the patch-id branch of D6. A change re-applied by a direct commit, `git cherry-pick -x` included, is then listed under Direct commits in the release that brings it back. Before the extension, such a commit was taken for a copy of the original pull request's commit and left out as already shipped, so the change it brought back was missing from the notes. The warning such a commit drew, that it was neither made by GitHub nor a pick of a commit GitHub made, now names the pull request and the commit whose change it re-applies.

9c was ruled (a): a pull request merged at GitHub's default title takes the title GitHub records now, not the first line of the merge's body, the title at the time of merging. Only merges already in the history are affected, since squash commits and titled merges carry the title in git. The two agree in 68 of 71 cases and no group changes in the data; in the three that differ, all in smalt-mcp and retitled between 18 seconds and 22 minutes after merging, the later title is the broader description on the reading made for the ruling; and the script reads GitHub's record in any case, so the body's title would not have made it independent of GitHub.

9d was ruled (a): a commit that changes nothing is bookkeeping, left out of the notes and reported in the job summary, since it is no change a reader of the notes can use. No such commit occurs in the data.

The acceptance run in dev-tools records the rulings on the rule that it relies on, dated, under ["Decided"](https://github.com/ParkviewLab/dev-tools/blob/main/tests/acceptance/README.md#decided); a difference from a recorded list is a ruled change there only when a ruling recorded in that section made it.

## 2026-09-18: the switch pull requests that edit `CHANGELOG.md`

The build's third open point was ruled the same day: each pull request that switches a repository to the shared generator and edits its `CHANGELOG.md`, paper-boxing's in the pilot and seven in the rollout, is merged only while no release of that repository is in progress, and the coordinating session says when each is safe. A release's back-merge carries the release job's own `CHANGELOG.md` commit to `develop`, and an edit of the same file on `develop` between the promotion and the back-merge could conflict with it. The ruling covers these eight pull requests alone; the same rule as a standing one belongs to the companion proposal for real merges.

## 2026-09-18: the release gate for the script, and dev-tools' own notes

NR01 was ruled (c): the constructed-history unit tests are the release gate for dev-tools, and the acceptance run over the 84 recorded releases stops being a precondition of a dev-tools release; it stays as the dated record of how the rule was validated, runnable by hand. The review had found that making the full run a precondition tied dev-tools' releases to the live state of the ten measured repositories, where a tag moved, a title edited or a new ref could fail a release with the script unchanged. The reason given with the ruling: the ten repositories were a census of those that existed in September 2026, an accident, and may be archived or replaced, and a test is not to rest on an accident. dev-tools' README states the practice that replaces the run: when a real release anywhere produces a wrong list, the shape of history that caused it becomes a new constructed test. The per-tag and release-check modes of the acceptance run remain as tools.

The real-history check refined that ruling the same day. Before any dev-tools release that changes the script, a dry run on the latest release of one representative repository per publishing profile is compared with that release's published list, or, before the representative has released with the shared generator, with its recorded result. One repository per profile suffices because each profile runs the changelog job inside a different release workflow, and the representatives were to be chosen for their differences, each with a reason, rather than at random. The set is defined by profile, not by name: an archived representative is replaced by the next repository of its profile, and a profile with none left leaves the set with its reason recorded. The unit tests remain the gate for the rule itself. dev-tools v1.2.0 was the first release made under this gate: the unit tests passed in CI, and the real-history check passed for all five representatives at the bump commit.

The profiles were first named by language, and were relabelled the same day by version file and publish target (T7 of the release-by-target rulings, recorded in [`releases-why.md`](releases-why.md) and made in [dev-tools #10](https://github.com/ParkviewLab/dev-tools/pull/10)), since the script reads the version file and its lock file to recognise version-bump commits and the project's name. The set as relabelled: `pyproject.toml` with GHCR, paper-boxing; `pyproject.toml` with PyPI, cogrind-workshop; `pyproject.toml` with PyPI and GHCR, smalt-mcp, which has the largest history and the longest log; `package.json` with npm and GHCR, jonobones; `package.json` with installers, pensa-grex, which has the longer release history; `Cargo.toml` with installers, pending until pensa-forma has releases; and npm only, pending. "Node, GHCR only" left the set, its two dimensions being covered by paper-boxing and jonobones.

NR03 was ruled and applied on 2026-09-18: `test` is a required check on dev-tools' `develop`, beside `reuse` and `no-version-change`. The review had found that the unit tests are the only automatic check of a script every repository's release runs, whilst `develop` required only the other two.

NR08 was ruled (a): dev-tools keeps GitHub's generated notes under the `release-txt.yml` profile, as the handbook does, and its `release.yml` stays identical to the template. The reason: one profile for both repositories whose version lives in `VERSION.txt`, and dev-tools' releases do not depend on the script they release. The review had found the template's stated reason, that such a repository has no Conventional Commit signal to categorise, false of dev-tools; the correction, that these repositories publish no package and that GitHub's notes list every pull request with its link, was made by the release-by-target change, which went first ([`releases-why.md`](releases-why.md)).

CC05 and DR10 were ruled (a): the Markdown under dev-tools' `tests/`, the acceptance run's README and the evidence reports, is licensed CC-BY-4.0 through one `REUSE.toml` annotation, with `LICENSING.md` and the README saying so, and the code there stays AGPL-3.0-or-later, as the handbook's per-bucket licensing gives it. Made in [dev-tools #9](https://github.com/ParkviewLab/dev-tools/pull/9).

## 2026-09-18: the tag ruleset tried and applied, and dev-tools' `main` protected

In the evening of that day, at 03:19 UTC on 2026-09-19, the ruleset of decision 8 was tried on a private scratch repository in the organisation before being applied anywhere: "Release tags", on tags matching `refs/tags/v*`, updates and deletions restricted, force pushes blocked, no bypass actor, active. From an account holding the organisation's administrator role, the push of `v0.0.1` succeeded, since a release must still be taggable; a move by force push, a deletion by `git push`, a deletion through the REST API and a move through the REST API were each refused, git answering "GH013: Repository rule violations found" with "Cannot update this protected ref" or "Cannot delete this tag", and the REST API answering HTTP 422 with the same messages. The tag ended where it began, and GitHub reported `current_user_can_bypass: never` for that account. The inference behind decision 8, that with no bypass actor no one passes, was confirmed. The scratch repository was then deleted.

At 03:24 UTC dev-tools' `main` was protected against force pushes and deletions by the call in [`ci.md`](ci.md#repo-merge-settings), and read back identical to paper-boxing's. At 03:48 UTC the ruleset was applied to dev-tools from the definition the trial had used, and read back active with an empty bypass list, GitHub reporting `current_user_can_bypass: never`. The convention auditor then found no deviation in dev-tools' `main` protection, or in its `release.yml` against the `release-txt.yml` of handbook v0.24.0.
