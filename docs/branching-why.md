# Branching and merging: the reasoning, the evidence and the decisions

This file is the second half of the record of the branching and merge model. The line between the two is what a reader needs: [`branching.md`](branching.md), with [`releases.md`](releases.md) and [`ci.md`](ci.md), keeps every rule and every reason needed to apply one, and this file adds what is needed only to reopen a decision, which is the measurement the rules rest on, the alternatives set aside, and the dated rulings. Entries are in date order and the record at the foot summarises them. The 2026-09 decisions were proposed on the organisation's wiki, in the book "Real merges and the back-merge pull request"; everything needed to reopen them is here, since a convention's reasons belong in the repository (axiom 3).

It is a record, so it describes the past and keeps doing so ([`documentation.md`](documentation.md#documents-and-records)). An open question does not belong here; one about branching as it now stands goes to [`in-flight_ideas.md`](in-flight_ideas.md), which holds two of them: whether axiom 4 should say that a gate the flow bypasses routinely is no gate, and what remains of D1 below.

## 2026-07: the two trunks kept, and the tax automated instead

Decided in July 2026: keep the permanent two-trunk model, `develop` integrating and `main` released, rather than move to release-from-main (D1 in [`handbook-improvements_ideas.md`](handbook-improvements_ideas.md), the 2026-07 survey that raised it).

The prevailing guidance, DORA's and Atlassian's, classes a permanent `develop` as legacy, superseded by trunk-based development. It was weighed and found weaker here than it looks. The organisation already integrates through short-lived branches, so it does not suffer the delayed integration that trunk-based development exists to remove; it merely keeps a second permanent line, and that line earns its keep three ways. `main` advancing only at a release is what makes its tip the released state, which is what a read-consumed repository is depended on for, the handbook above all, whose pointer files reference `/tree/main` for exactly that reason. The two trunks give a legible structural map, `develop` the integration and dev-build surface and `main` the release surface, that one trunk would trade for a subtler distinction drawn in tags and workflows. And retiring `develop` would be a family-wide migration touching every repository's protection, the version guard's base, the release gate, the `dev-tools` scripts and the website profile, all to remove a bounded and self-correcting cost.

The cost the model does carry is the back-merge after every release, and the decision was to automate it rather than to change the model. D1's own design for that automation is superseded by the ruling of 2026-09-18 below, in four respects: its helper merged `main` into `develop` and pushed, where the push is the bypass this proposal removes; it opened the next cycle with `git dev-release --open` after that push, where the cycle now travels inside the pull request and cannot land before the back-merge does; it fanned `develop` out into each open working worktree, where the helper now lists those branches and merges into none, because under real merges each such merge becomes permanent history of that branch and the up-to-date rule already brings a branch current before its pull request merges; and it named `git dev-release --open` as the permanent route, where that command now refuses in a repository that has switched.

Two parts of D1 remain open and are in [`in-flight_ideas.md`](in-flight_ideas.md): the promotion's staleness guard, which would refuse `git merge --no-ff develop` while local `develop` differs from `origin/develop`, and folding the release flow into a release skill.

D1 asked for the two-trunk choice to be recorded as a decision record, and noted on 2026-09-17 that a `branching-why.md` sibling was a third candidate form for it, beside a single `docs/decisions.md` and a per-decision directory, and that a second page earning such a sibling was the point at which the form's rule should be reviewed. This file is that form. The rule was reviewed with it and now states the pair's division of labour and names the four siblings, in place of the ordinals it had been keeping ([`documentation.md`](documentation.md#documents-and-records)).

## 2026-09-18: the version guard's depth-one fetch

Every one of the thirteen copies of `version-guard.yml` checked out with `fetch-depth: 0` and then ran `git fetch --no-tags --depth=1 origin "$BASE"`. The first step has already fetched every branch and tag in full; the second writes `develop`'s tip into `.git/shallow`, so git treats that commit as parentless. Reproduced against the handbook's history with an Actions-style checkout of a synthetic pull-request merge: the history reachable from `origin/develop` fell from 126 commits to 1, every ancestry test against `develop` but its own tip failed, and merge bases through that tip were lost; in the release window, with `develop` an ancestor of `main`, `main` and the new tag lost history too and the previous back-merge became unreachable. No object is deleted, so the clone keeps every commit: what falls to one is the history reachable from `origin/develop`.

The guard as it then stood was unaffected, because it read only `origin/$BASE:<file>`, that tip's own tree. The back-merge mode below cannot be, since its ancestry and merge-base tests walk through `develop`'s tip, so the line had to go before the mode could be added.

Ruled 2026-09-18: removed at once, everywhere — one handbook pull request carrying the template and the handbook's own copy, a handbook release, then one pull request in each of the other twelve repositories. The lighter route, the template now and each other repository with its next workflow change, was offered and not taken. The scope was widened the same day to the two private repositories of the `garycoding` account that also carried the line. The fix is complete: the handbook released it as v0.24.0, and fourteen further pull requests carried it, after which every copy differed from the template only by its SPDX header and two documented local rules.

## 2026-09-18: real merges, and the release's back-merge by pull request

The ruling of 18 September 2026: pull requests into `develop` are merged with real merge commits titled `<PR title> (#N)`, squash merging is disabled, and the release's back-merge and the dev cycle it opens reach `develop` through a checked pull request rather than a direct push. [`branching.md`](branching.md) and [`releases.md`](releases.md#after-the-release-the-back-merge-pull-request) state the rules; [`ci.md`](ci.md#repo-merge-settings) holds the settings and the guard.

### The measured problem

Measured on 17 September 2026 from the thirteen repositories that run the version guard, GitHub's REST API and the repository activity endpoint, which records every push, merge, force push and ref deletion. Six writes in the release flow reached a trunk without a pull request: the promotion, the bump and tag, the changelog job's commit, the back-merge, the open-cycle bump, and each dev build. Over the last three releases of each repository — 31 releases — there were 39 direct pushes to `develop` and 3 more for dev builds. All 31 back-merges were direct pushes, and 23 of them were fast-forwards, which the documented `--no-ff` command does not produce; all 24 open-cycle commits were direct pushes.

No check ran before any of them landed. `main` had no required checks in any repository. `develop` required checks in all thirteen, but with `enforce_admins` false, and every push was made by an account holding the organisation's administrator role, so each landed by the bypass that [`ci.md`](ci.md#required-checks-before-merge) then prescribed. What ran afterwards was whatever the push triggered, on the head of the push rather than on each commit it carried; where a back-merge fast-forwarded onto the `[skip ci]` changelog commit, nothing ran at all. The version guard, which triggers on pull requests, never examined a back-merge at all.

Two further facts shaped the design. Tags are unprotected and the activity endpoint records six deletions of release tags, most followed by re-creation at another commit; and two force pushes to `main` are recorded, both on 20 July 2026. So "reachable from `main`" is a weaker statement than it looks, which is why the check names the tag rather than trusting `main` (decision 8 below).

### The four courses, and why real merges

Set aside, keeping squash merging and verifying each direct push after it lands: the guard would gain a push-triggered mode that runs the back-merge check on every push to `develop` that merges `main`, and a helper would make every back-merge a `--no-ff` merge so that the check had one merge to examine. It is the cheapest course and changes no setting, and it would report a bad back-merge seconds after it landed. What it leaves is the direct push itself: the bypass and its notice at every release, a write that nothing gates, a failure repaired after the fact on a shared trunk, and the dev-build pushes unchanged.

Set aside, keeping squash merging and landing a checked back-merge by a fast-forward push: the helper would open the back-merge as a draft pull request, which offers no merge button and so cannot be squashed, and once `develop`'s required checks had passed on its head, `git push origin <head-sha>:develop` would fast-forward `develop` to it. GitHub documents that commits which have passed the required checks may be pushed to a protected branch, and that a pull request is marked merged when its head becomes reachable from the base outside it. Two behaviours were unverified, however: whether GitHub accepts that push without the bypass, and whether a draft pull request is marked merged that way. The recommended course depends on no unverified behaviour, which is what separated them, since in their gate they do not differ: each is gated by the helper's refusal until administrators are bound, and by GitHub after.

Set aside, allowing merge commits beside squash merging: GitHub sets the allowed merge methods for the whole repository, or by a ruleset for the branches merged into, never by a pull request's head branch, so once merge commits are allowed for `develop` at all the button offers both methods for every pull request into it. A back-merge that is squashed severs `develop` from the release: the tag is no longer an ancestor of `develop`, and the three things that read that ancestry — `git back-merge`'s own test of whether the back-merge has landed, the release preflight's check, and `git dev-release`'s reading of the last release — all misread the state, whilst the next promotion conflicts on the version line exactly as it would with no back-merge at all, because the merge base of the two trunks stays the commit promoted for the previous release. Both were reproduced in a scratch repository.

Chosen: real merges, with the back-merge pull request merged by GitHub's own merge. It is the only course that lands every release write through `develop`'s protection by a documented mechanism, the same one that made the 71 real merges already in the measured history of the ten repositories that have released.

### What it costs, and what it gives

Accepted, with what meets each. Every commit of a merged branch becomes permanent history, including the commits that the contract's rule to push after each commit produces, and so do the merges of `develop` that the up-to-date rule forces in the eleven repositories that require it; those sit on the second-parent side, so the first-parent ledger does not show them and the changelog counts them as part of their pull request. A plain `git log`, `git bisect` and `git blame` traverse the branch commits, and bisection can stop on a working commit that never built; `git bisect start --first-parent` keeps the search to the pull-request merges. Reverting a merged pull request needs `git revert -m 1`, after which its changes return only by reverting the revert, which the narrowing of the changelog rule's D8 and D6 makes listable in the release that brings them back ([`commits-and-changelogs-why.md`](commits-and-changelogs-why.md)). A `BREAKING CHANGE:` footer written in a branch commit no longer reaches the commit that represents the pull request, because the merge message is the description rather than the gathered commit messages; the shared generator looks in both, and the rule now says the footer belongs in the description. A pull request picked onto `main` for a hotfix is now a merge, so it is picked whole with `git cherry-pick -m 1` and listed once by its number.

Three things the handbook gave as reasons for squash merging are kept rather than given up. The pull request's title still carries its Conventional Commit type, by `merge_commit_title=PR_TITLE`. There is still one dated commit per feature on `develop`'s first-parent line, dated when the pull request merged. And there is still one allowed method and no wrong option on the button, by disabling squash merging (decision 2).

What real merges give, beyond meeting the back-merge's need: a branch's commits are kept in the repository rather than only on GitHub's pull-request page, which serves intent 2, and blame and bisect can reach them; and after a merge the branch tip is an ancestor of `develop` again, so the cleanup's ancestry test answers the question it is asked and the exception that squash merging forced on it goes.

### Who merges the back-merge pull request (decision 3)

The release ask covers it. The contract already placed the back-merge under that ask, so the pull request changes the form of an act the ask covered, not its scope; and the ask also covers the helper's force push of its own `back-merge-<tag>` branch when it refreshes it, and nothing else. The releaser merges only after all of `develop`'s required checks have passed on the head, with `gh pr merge --merge --match-head-commit`, never with `--admin`, so the commit that lands is the one the check examined. Axiom 4 is kept: the explicit human hand it requires for a merge to a shared trunk is the release ask, asked for per release and never inferred. The consequences accepted are that a release no longer ends when the last push is made, since the releaser waits for `develop`'s checks, and that the back-merge is the first pull request into `develop` that an agent merges itself.

Set aside: a person merges it, which would leave the release complete only when they had, `develop` without the release meanwhile, and the next release's preflight stopping while it was open. Set aside: GitHub's auto-merge, which would need `allow_auto_merge` enabled in every repository and would then offer auto-merge on every pull request, including the feature pull requests only a person may merge.

### The open cycle (decision 4)

The open-cycle bump travels as the second commit of the back-merge pull request, where the guard verifies it. It then cannot be made before the back-merge has landed, which an earlier review showed produces a dev version below the release and a conflict on the version line.

Set aside: the bump in a pull request of its own, which would need a third guard mode admitting exactly the placeholder and would make every release wait on two pull requests. Set aside: the bump as a direct push, which would leave one bypass per release in every code repository and would keep administrators from being bound. Set aside: no committed dev version at all, which would have `develop` report the last released version between releases, the very thing the honest-pre-release rule exists to prevent.

### The dev builds (decision 5)

A dev build takes its version in the build's workspace and commits nothing: the gate computes it from the newest release tag, the `kind` input and the run, and each building job writes it into the version file in its own workspace before building.

The evidence for it: the dev workflows read the version only from the working tree, so nothing in them requires it to be a commit; `uv version 0.1.2.dev17` rewrote `pyproject.toml` and `uv.lock` together and `uv build` then produced a distribution of that version, and `npm version --no-git-tag-version` did the same for `package.json` and its lockfile. Two constraints fix the build number: PyPI and TestPyPI never accept a file name twice, and `github.run_number` does not change when a run is re-run, so N combines it with `github.run_attempt`. The placeholder stays committed once per release, so `develop` still reports an honest pre-release version to `/admin/version`, an editable install and a locally built image.

Set aside: a committed version per build pushed directly, as before, which leaves one bypass per dev build and keeps administrators from being bound. Set aside: a committed version per build through a pull request, which would make every dev build wait for a guard mode, for `develop`'s checks and for a merge.

Three consequences were accepted. A re-point to a minor or major target is an input of each build and no longer persists between builds, so the published dev version may name a different target from the placeholder `develop` reports. And the record of which commit a build came from moves from a `chore: dev build` commit to the workflow run and the image's `sha-<commit>` tag. Ruled 2026-09-27, for the case the design left open: in a repository with no release tag yet the target is the version file's own version with any dev marker removed, and the kind is not used.

### Where the check lives, and tag mode (decisions 7 and 8)

The check is one script in `dev-tools`, `back-merge-check`, which the version guard checks out at a pinned release and runs in its back-merge mode, and which `git back-merge` runs on its own result before it pushes. One rule then applies in both places, and the rule deciding what a back-merge pull request may bring into `develop` changes only when a repository moves its pin. Set aside: the check's text carried inline in the guard template, with a second copy inside the helper for its own verification, which would have been the same rule written twice.

Tag mode is required: every commit the merge brings from `main` must be in the tag the branch names, or be that tag's changelog commit, and `main`'s version must equal the tag's. That is what makes the check independent of `main`'s protection, which most repositories do not have, and of the tags' own, which nothing enforced when the design was made. Set aside: treating any commit on `main` as released, which would admit whatever had reached `main` since the tag.

The mode is chosen inside the one required job, because a job selected by an `if:` condition reports success when it is skipped, and a pull request could then satisfy the required context by its branch name alone. The check is evaluated on explicit commits rather than on the checked-out `HEAD`, which on a `pull_request` event is GitHub's synthetic merge of the head into the base: a check computed from `HEAD` would find two merges not on `main` and refuse every back-merge. The base is that synthetic merge's first parent rather than the event's `base.sha`, whose refresh rule GitHub does not document, so that a branch rebuilt from a newer `develop` is judged against the tip its run was tested against.

### The check, simulated before it was built

The check was written first as a simulation, 224 lines of bash, and run against constructed histories. The main history was built with `dev-tools`' own `git bump`, `git release` and `_sot.sh`, so the placeholder arithmetic and the lockfile rewriting were the production code: a release on `main`, a cycle opened on `develop`, a feature merged before the release and another during it, the changelog commit made by `github-actions[bot]` after the tag, and then the back-merge built from `origin/develop` with the open-cycle commit on top. All 24 cases of that scenario gave the expected result under bash 3.2 with git 2.54, 21 of them were replayed under bash 5.2 with git 2.49, and 6 further cases covered `package.json` and `VERSION.txt` repositories.

The simulation changed the design in one respect before anything was built: condition 4 was narrowed to refuse an open-cycle commit in a `VERSION.txt` repository, which skips the open cycle, where the simulation had admitted one.

### A conflicting back-merge (decision 6)

For a conflict on the version line, which means a version change reached `develop` during the release: one reviewed commit restoring `develop`'s version lines to the version promoted, pushed directly, with `enforce_admins` switched off and on again where administrators are bound, and then the back-merge again. For any other conflict: an ordinary pull request into `develop` bringing `develop`'s side of each conflicting passage into agreement with `main`'s, and then the back-merge rebuilt. `git back-merge` refuses before merging in both cases and names the repair, so nothing lands half-resolved.

Prevention comes before both, and one rule of it is standing from this ruling: no pull request that edits `CHANGELOG.md` is merged into `develop` between a promotion and its back-merge, that file being where the release's own commit lands. It was first ruled on 2026-09-18 for the eight switch pull requests of the changelog build, which each edited that file, and it is general here.

### Administrators bound on `develop` (decision 9)

With the back-merge and the open cycle arriving by pull request and dev builds committing nothing, no step of the flow writes to `develop` except a merge through its protection, so each repository's `develop` sets `enforce_admins` true once its first back-merge pull request has merged. The owner, as administrator, is bound too. The condition is what proves the flow in that repository before the bypass goes; a repository that makes no release is bound from its switch, since nothing there ever pushes to `develop`. Binding changes nothing in the flow and makes `develop`'s checks a gate for every write, including a mistaken one; an emergency write then needs the setting switched off, which is an explicit change to the repository's settings rather than a routine consequence of the flow.

Set aside: leaving the bypass in place on the ground that the flow no longer needs it, which would leave every bypass notice indistinguishable from the routine ones that raised the question in the first place.

### The position this revises

[`releases.md`](releases.md) had recorded, since the handbook's first commit of 14 June 2026, that "the cascade is manual on purpose (a small number of commands at a moment the user is already at the keyboard; an auto-PR version was considered and declined)". No reason for the decline was kept, so it cannot be answered on its own terms. This ruling revises the position rather than reversing it: the back-merge is still a step the releaser runs at the keyboard by one command at the same moment, so the recorded reason still holds and is kept, and it is not an automatic pull request opened by a trigger. What the decline did not weigh is the reason for the change: that the direct push bypasses `develop`'s protection at every release, that the version guard never examines the back-merge, and that 23 of the last 31 back-merges departed from the documented `--no-ff` with nothing reporting it.

Three further statements changed with it. Squash-only settings were given as the reason for a local promotion, which no longer holds; the promotion keeps the reasons that do, namely that `main` carries no required checks for a promotion pull request to wait for, that such a pull request would add a second wait to every release, and that the release ask is the explicit hand it needs. The administrators' bypass was prescribed for the back-merge and the promotion, which the back-merge no longer needs and the promotion never did, since it pushes `main`. And the open cycle was described as a direct push "exempt from `version-guard.yml`, like the back-merge itself"; it is now the verified second commit of the back-merge pull request.

## 2026-09-26: the three points the design left inconsistent

Settled when the command was built, each following from the design and changing no ruling.

`git back-merge` takes an existing pull request's head as current only if `back-merge-check` passes on it, and otherwise rebuilds the branch. As the design had it, a head that already contained `develop`'s tip went straight to the checks, which is wrong after someone has pressed GitHub's "Update branch": that head carries a second merge commit, the check refuses it, and the command would have stopped on a failing guard although the pull request's own body promises that a second run refreshes it.

Step 3 finds the transition section of the released `docs/releases.md` by its exact heading, "Until a repository has switched", and quotes it where it refuses; until that section was released it quoted the "After the release" section instead, and only while that section still gave the direct back-merge. The heading is therefore a contract between the two repositories, and renaming the section breaks the refusal's message.

`git dev-release` refuses a committing dev build, not only `--open`, once a repository allows merge commits. The design kept the old behaviour wherever the workflow had no `kind` input, but after the switch that behaviour would push to `develop`, which then takes no direct push (decision 9).

## 2026-09-26: the repositories the rule reaches

The thirteen repositories that run the version guard switch in the order the build sets, each after it has switched to the shared changelog generator, since the notes would otherwise list every branch commit. Four repositories outside that set were ruled on the same day.

`vos-gspheres`, a private repository of the `garycoding` account that follows the handbook by adoption, comes under this rule: merge commits as its only merge method, `develop` and `main` protected, and its administrators bound at its switch rather than at a first back-merge, since under its owner's policy of 2026-07-04 it makes no release and so nothing ever pushes to `develop` there. Its release apparatus stays dormant. `yucca-basing`, a Rust exploration begun before PensaForma was chosen as the first Rust desktop application and very probably no longer needed, is left as it is on squash merging; the removal of the transition section does not wait for it. `hazel-tracking` meets the rule at its creation, being scaffolded under the conventions released by then, rather than by a switch pull request. `pvl-dotview` comes under the rule directly when it is aligned with the handbook, without first being restricted to squash merging: it writes no release notes for a generator to spoil and it already merges with merge commits, so restricting it first would be undone one release later.

`pensa-forma` switches with its first release rather than with the other code repositories, because its version lives in `Cargo.toml`: both the back-merge's check and the open cycle read the version file, and its first release needs that reading in any case.

## 2026-09-27: a head that `develop` has moved beyond

Ruled 2026-09-27, restating what the design requires rather than changing it: a head that `develop` has moved beyond is never merged, and `git back-merge` rebuilds the branch from the new `develop`, whichever check stops it. Where the repository requires branches to be up to date there are two, and the earlier wording named only the second: the command's own test, before it asks for the merge, that `origin/develop` is an ancestor of the head, and GitHub's refusal of an out-of-date merge if it does ask. The command tries three rebuilds and then leaves the pull request open. Where a repository does not require up-to-date branches there is nothing to rebuild for: GitHub's merge carries the newer `develop`, and what the back-merge brings is still exactly what the check examined.

Set aside: test-only code in the released script, to suppress its own check so that GitHub's refusal could be exercised deliberately. A released command would then carry a path that exists for its test, and GitHub's refusal is covered by `dev-tools`' own tests, where the fake GitHub answers as GitHub does.
