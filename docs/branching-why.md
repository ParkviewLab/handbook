# Branching and merging: the reasoning, the evidence and the decisions

This file is the second half of the record of the branching and merge model. The line between the two is what a reader needs: [`branching.md`](branching.md), with [`releases.md`](releases.md) and [`ci.md`](ci.md), keeps every rule and every reason needed to apply one, and this file adds what is needed only to reopen a decision, which is the measurement the rules rest on, the alternatives set aside, and the dated rulings. Entries are in date order and the record at the foot summarises them. Dates are those of America/Los_Angeles, the time zone in which the rulings were made, and a time, where one is stated, is UTC. The 2026-09 decisions were proposed on the organisation's wiki, in the book "Real merges and the back-merge pull request"; everything needed to reopen them is here, since a convention's reasons belong in the repository (axiom 3).

It is a record, so it describes the past and keeps doing so ([`documentation.md`](documentation.md#documents-and-records)). An open question does not belong here; one about branching as it now stands goes to [`in-flight_ideas.md`](in-flight_ideas.md), which holds two of them: whether axiom 4 should say that a gate the flow bypasses routinely is no gate, and what remains of D1 below.

## 2026-07: the two trunks kept, and the tax automated instead

Decided in July 2026: keep the permanent two-trunk model, `develop` integrating and `main` released, rather than move to release-from-main (D1 in [`handbook-improvements_ideas.md`](handbook-improvements_ideas.md), the 2026-07 survey that raised it).

The prevailing guidance, DORA's and Atlassian's, classes a permanent `develop` as legacy, superseded by trunk-based development. It was weighed and found weaker here than it looks. The organisation already integrates through short-lived branches, so it does not suffer the delayed integration that trunk-based development exists to remove; it merely keeps a second permanent line, and that line earns its keep three ways. `main` advancing only at a release is what makes its tip the released state, which is what a read-consumed repository is depended on for, the handbook above all, whose pointer files reference `/tree/main` for exactly that reason. The two trunks give a legible structural map, `develop` the integration and dev-build surface and `main` the release surface, that one trunk would trade for a subtler distinction drawn in tags and workflows. And retiring `develop` would be a family-wide migration touching every repository's protection, the version guard's base, the release gate, the `dev-tools` scripts and the website profile, all to remove a bounded and self-correcting cost.

The cost the model does carry is the back-merge after every release, and the decision was to automate it rather than to change the model. D1's own design for that automation is superseded by the ruling of 2026-09-18 below, in four respects: its helper merged `main` into `develop` and pushed, where the push is the bypass that ruling removes; it opened the next cycle with `git dev-release --open` after that push, where the cycle now travels inside the pull request and cannot land before the back-merge does; it fanned `develop` out into each open working worktree, where the helper now lists those branches and merges into none, because under real merges each such merge becomes permanent history of that branch and the up-to-date rule already brings a branch current before its pull request merges; and it named `git dev-release --open` as the permanent route, where that command now refuses in a repository that has switched.

Two parts of D1 remain open and are in [`in-flight_ideas.md`](in-flight_ideas.md): the promotion's staleness guard, which would refuse `git merge --no-ff develop` while local `develop` differs from `origin/develop`, and folding the release flow into a release skill.

D1 asked for the two-trunk choice to be recorded as a decision record, and noted on 2026-09-17 that a `branching-why.md` sibling was a third candidate form for it, beside a single `docs/decisions.md` and a per-decision directory, and that a second page earning such a sibling was the point at which the form's rule should be reviewed. This file is that form. The rule was reviewed with it and now states the pair's division of labour and names the four siblings, in place of the ordinals it had been keeping ([`documentation.md`](documentation.md#documents-and-records)).

## 2026-09-18: the version guard's depth-one fetch

Every one of the thirteen copies of `version-guard.yml` checked out with `fetch-depth: 0` and then ran `git fetch --no-tags --depth=1 origin "$BASE"`. The first step has already fetched every branch and tag in full; the second writes `develop`'s tip into `.git/shallow`, so git treats that commit as parentless. Reproduced against the handbook's history with an Actions-style checkout of a synthetic pull-request merge: the history reachable from `origin/develop` fell from 126 commits to 1, every ancestry test against `develop` but its own tip failed, and merge bases through that tip were lost; in the release window, with `develop` an ancestor of `main`, `main` and the new tag lost history too and the previous back-merge became unreachable. No object is deleted, so the clone keeps every commit: what falls to one is the history reachable from `origin/develop`.

The guard as it then stood was unaffected, because it read only `origin/$BASE:<file>`, that tip's own tree. The back-merge mode below cannot be, since its ancestry and merge-base tests walk through `develop`'s tip, so the line had to go before the mode could be added.

Ruled 2026-09-18: removed at once, everywhere (one handbook pull request carrying the template and the handbook's own copy, a handbook release, then one pull request in each of the other twelve repositories). The lighter route, the template now and each other repository with its next workflow change, was offered and not taken. The scope was widened the same day to the two private repositories of the `garycoding` account that also carried the line. The fix is complete: the handbook released it as v0.24.0, and fourteen further pull requests carried it, after which every copy differed from the template only by its SPDX header and two documented local rules.

## 2026-09-18: real merges, and the release's back-merge by pull request

The ruling of 18 September 2026: pull requests into `develop` are merged with real merge commits titled `<PR title> (#N)`, squash merging is disabled, and the release's back-merge and the dev cycle it opens reach `develop` through a checked pull request rather than a direct push. [`branching.md`](branching.md) and [`releases.md`](releases.md#the-releases-last-step-the-back-merge-pull-request) state the rules; [`ci.md`](ci.md#repo-merge-settings) holds the settings and the guard.

### The measured problem

Measured on 17 September 2026 from the thirteen repositories that run the version guard, GitHub's REST API and the repository activity endpoint, which records every push, merge, force push and ref deletion. Six writes in the release flow reached a trunk without a pull request: the promotion, the bump and tag, the changelog job's commit, the back-merge, the open-cycle bump, and each dev build. Over the last three releases of each repository (31 releases) there were 39 direct pushes to `develop` and 3 more for dev builds. All 31 back-merges were direct pushes, and 23 of them were fast-forwards, which the documented `--no-ff` command does not produce; all 24 open-cycle commits were direct pushes.

No check ran before any of them landed. `main` had no required checks in any repository. `develop` required checks in all thirteen, but with `enforce_admins` false, and every push was made by an account holding the organisation's administrator role, so each landed by the bypass that [`ci.md`](ci.md#required-checks-before-merge) then prescribed. What ran afterwards was whatever the push triggered, on the head of the push rather than on each commit it carried; where a back-merge fast-forwarded onto the `[skip ci]` changelog commit, nothing ran at all. The version guard, which triggers on pull requests, never examined a back-merge at all.

Two further facts shaped the design. Tags are unprotected and the activity endpoint records six deletions of release tags, most followed by re-creation at another commit; and two force pushes to `main` are recorded, both on 20 July 2026. So "reachable from `main`" is a weaker statement than it looks, which is why the check names the tag rather than trusting `main` (decision 8 below).

### The four courses, and why real merges

Set aside, keeping squash merging and verifying each direct push after it lands: the guard would gain a push-triggered mode that runs the back-merge check on every push to `develop` that merges `main`, and a helper would make every back-merge a `--no-ff` merge so that the check had one merge to examine. It is the cheapest course and changes no setting, and it would report a bad back-merge seconds after it landed. What it leaves is the direct push itself: the bypass and its notice at every release, a write that nothing gates, a failure repaired after the fact on a shared trunk, and the dev-build pushes unchanged.

Set aside, keeping squash merging and landing a checked back-merge by a fast-forward push: the helper would open the back-merge as a draft pull request, which offers no merge button and so cannot be squashed, and once `develop`'s required checks had passed on its head, `git push origin <head-sha>:develop` would fast-forward `develop` to it. GitHub documents that commits which have passed the required checks may be pushed to a protected branch, and that a pull request is marked merged when its head becomes reachable from the base outside it. Two behaviours were unverified, however: whether GitHub accepts that push without the bypass, and whether a draft pull request is marked merged that way. The chosen course depends on no unverified behaviour, which is what separated them, since in their gate they do not differ: each is gated by the helper's refusal until administrators are bound, and by GitHub after.

Set aside, allowing merge commits beside squash merging: GitHub sets the allowed merge methods for the whole repository, or by a ruleset for the branches merged into, never by a pull request's head branch, so once merge commits are allowed for `develop` at all the button offers both methods for every pull request into it. A back-merge that is squashed severs `develop` from the release: the tag is no longer an ancestor of `develop`, and the three things that read that ancestry (`git back-merge`'s own test of whether the back-merge has landed, the release preflight's check, and `git dev-release`'s reading of the last release) all misread the state; and in a code repository the next promotion conflicts on the version line, because the merge base of the two trunks stays the commit promoted for the previous release, and since then `main` has changed that line to the version released and `develop` to the next cycle's placeholder. Both were reproduced in a scratch repository. A documents repository has no open cycle, so there a squashed back-merge changes the line as `main` did and the promotion does not conflict. And under this flow, where the back-merge is skipped altogether, the next promotion is clean in every repository, since `develop` then still carries the version that was promoted; only the tag stays outside `develop`'s ancestry.

Chosen: real merges, with the back-merge pull request merged by GitHub's own merge. It is the only course that lands every release write through `develop`'s protection by a documented mechanism, the same one that made the 71 real merges already in the measured history of the ten repositories that have released.

### What it costs, and what it gives

Accepted, each with its mitigation: Every commit of a merged branch becomes permanent history, including the commits that the contract's rule to push after each commit produces, and so do the merges of `develop` that the up-to-date rule forces in the eleven repositories that require it; those sit on the second-parent side, so the first-parent ledger does not show them and the changelog counts them as part of their pull request. A plain `git log`, `git bisect` and `git blame` traverse the branch commits, and bisection can stop on a working commit that never built; `git bisect start --first-parent` keeps the search to the pull-request merges. Reverting a merged pull request needs `git revert -m 1`, after which its changes return only by reverting the revert, which the narrowing of the changelog rule's D8 and D6 makes listable in the release that brings them back ([`commits-and-changelogs-why.md`](commits-and-changelogs-why.md)). A `BREAKING CHANGE:` footer written in a branch commit no longer reaches the commit that represents the pull request, because the merge message is the description rather than the gathered commit messages; the shared generator looks in both, and the rule now says the footer belongs in the description. A pull request picked onto `main` for a hotfix is now a merge, so it is picked whole with `git cherry-pick -m 1` and listed once by its number.

Three things the handbook gave as reasons for squash merging are kept rather than given up. The pull request's title still carries its Conventional Commit type, by `merge_commit_title=PR_TITLE`. There is still one dated commit per feature on `develop`'s first-parent line, dated when the pull request merged. And there is still one allowed method and no wrong option on the button, by disabling squash merging (decision 2).

What real merges give, beyond meeting the back-merge's need: a branch's commits are kept in the repository rather than only on GitHub's pull-request page, which serves intent 2, and blame and bisect can reach them; and after a merge the branch tip is an ancestor of `develop` again, so the cleanup's ancestry test answers the question it is asked and the exception that squash merging forced on it goes.

### Who merges the back-merge pull request (decision 3)

The release ask covers it. The contract already placed the back-merge under that ask, so the pull request changes the form of an act the ask covered, not its scope; and the ask also covers the helper's force push of its own `back-merge-<tag>` branch when it refreshes it, and nothing else. The releaser merges only after all of `develop`'s required checks have passed on the head, with `gh pr merge --merge --match-head-commit`, never with `--admin`, so the commit that lands is the one the check examined. Axiom 4 is kept: the explicit human hand it requires for a merge to a shared trunk is the release ask, asked for per release and never inferred. The consequences accepted are that a release no longer ends when the last push is made, since the releaser waits for `develop`'s checks, and that the back-merge is the first pull request into `develop` that an agent merges itself.

Set aside: a person merges it, which would leave the release complete only when they had, `develop` without the release meanwhile, and the next release's preflight stopping while it was open. Set aside: GitHub's auto-merge, which would need `allow_auto_merge` enabled in every repository and would then offer auto-merge on every pull request, including every feature pull request, which the contract makes the user's merge ([`ai-collaboration.md`](ai-collaboration.md#shared-state-writes-need-explicit-authorization)).

### The open cycle (decision 4)

The open-cycle bump travels as the second commit of the back-merge pull request, where the guard verifies it. It then cannot be made before the back-merge has landed, which an earlier review showed produces a dev version below the release and a conflict on the version line.

Set aside: the bump in a pull request of its own, which would need a third guard mode admitting exactly the placeholder and would make every release wait on two pull requests. Set aside: the bump as a direct push, which would leave one bypass per release in every code repository and would keep administrators from being bound. Set aside: no committed dev version at all, which would have `develop` report the last released version between releases, the very thing the honest-pre-release rule exists to prevent.

### The dev builds (decision 5)

A dev build takes its version in the build's workspace and commits nothing: the gate computes it from the newest release tag, the `kind` input and the run, and each building job writes it into the version file in its own workspace before building. The gate carries its own copy of the increment, the arithmetic that `_sot.sh`'s `sot_compute_next` applies to a plain version, rather than checking `dev-tools` out to run it, because the copy adds no read of another repository: the dev workflow checks nothing out from `dev-tools` and has no pin to keep current.

The evidence for it: the dev workflows read the version only from the working tree, so nothing in them requires it to be a commit; `uv version 0.1.2.dev17` rewrote `pyproject.toml` and `uv.lock` together and `uv build` then produced a distribution of that version, and `npm version --no-git-tag-version` did the same for `package.json` and its lockfile. Two constraints fix the build number: PyPI and TestPyPI never accept a file name twice, and `github.run_number` does not change when a run is re-run, so N combines it with `github.run_attempt`. The placeholder stays committed once per release, so `develop` still reports an honest pre-release version to `/admin/version`, an editable install and a locally built image.

Set aside: a committed version per build pushed directly, as before, which leaves one bypass per dev build and keeps administrators from being bound. Set aside: a committed version per build through a pull request, which would make every dev build wait for a guard mode, for `develop`'s checks and for a merge.

Two consequences were accepted. A re-point to a minor or major target is an input of each build and no longer persists between builds, so the published dev version may name a different target from the placeholder `develop` reports. And the record of which commit a build came from moves from a `chore: dev build` commit to the workflow run and the image's `sha-<commit>` tag. Ruled 2026-09-26, for the case the design left open: in a repository with no release tag yet the target is the version file's own version with any dev marker removed, and the kind is not used.

### Where the check lives, and tag mode (decisions 7 and 8)

The check is one script in `dev-tools`, `back-merge-check`, which the version guard checks out at a pinned release and runs in its back-merge mode, and which `git back-merge` runs on its own result before it pushes. One rule then applies in both places, and the rule deciding what a back-merge pull request may bring into `develop` changes only when a repository moves its pin. Set aside: the check's text carried inline in the guard template, with a second copy inside the helper for its own verification, which would have been the same rule written twice.

Tag mode is required: every commit the merge brings from `main` must be in the tag the branch names, or be that tag's changelog commit, and `main`'s version must equal the tag's. That is what makes the check independent of `main`'s protection, which most repositories do not have, and of the tags' own, which nothing enforced when the design was made. Set aside: treating any commit on `main` as released, which would admit whatever had reached `main` since the tag.

The mode is chosen inside the one required job, because a job selected by an `if:` condition reports success when it is skipped, and a pull request could then satisfy the required context by its branch name alone. The check is evaluated on explicit commits rather than on the checked-out `HEAD`, which on a `pull_request` event is GitHub's synthetic merge of the head into the base: a check computed from `HEAD` would find two merges not on `main` and refuse every back-merge. The base is that synthetic merge's first parent rather than the event's `base.sha`, whose refresh rule GitHub does not document, so that a branch rebuilt from a newer `develop` is judged against the tip its run was tested against.

### The check, simulated before it was built

The check was written first as a simulation, 224 lines of bash, and run against constructed histories. The main history was built with `dev-tools`' own `git bump`, `git release` and `_sot.sh`, so the placeholder arithmetic and the lockfile rewriting were the production code: a release on `main`, a cycle opened on `develop`, a feature merged before the release and another during it, the changelog commit made by `github-actions[bot]` after the tag, and then the back-merge built from `origin/develop` with the open-cycle commit on top. All 24 cases of that scenario gave the expected result under bash 3.2 with git 2.54, 21 of them were replayed under bash 5.2 with git 2.49, and 6 further cases covered `package.json` and `VERSION.txt` repositories.

The simulation changed the design in one respect before anything was built: condition 4, as the header comment of [`back-merge-check`](https://github.com/ParkviewLab/dev-tools/blob/main/scripts/back-merge-check) numbers the conditions, was narrowed to refuse an open-cycle commit in a `VERSION.txt` repository, which skips the open cycle, where the simulation had admitted one.

### A conflicting back-merge (decision 6)

Decision 6 has two repairs, lettered (a) and (d) in the design. Repair (a), for a conflict on the version line, which means a version change reached `develop` during the release, is one reviewed commit restoring `develop`'s version lines to the version promoted, pushed directly, with `enforce_admins` switched off and on again where administrators are bound, and then the back-merge again. Repair (d), for any other conflict, is an ordinary pull request into `develop` bringing `develop`'s side of each conflicting passage into agreement with `main`'s, and then the back-merge rebuilt. `git back-merge` refuses before merging in both cases and names the repair, so nothing lands half-resolved. For a release picked onto `main`, the exception's direct back-merge took the place of (d) on 2026-09-27 (below).

Prevention comes before both, and one preventive rule dates from this ruling: no pull request that edits `CHANGELOG.md` is merged into `develop` between a promotion and its back-merge, that file being where the release's own commit lands. It was first ruled on 2026-09-18 for the changelog build's eight pull requests that moved repositories to the shared generator, each of which edited that file, and it is general here.

### Administrators bound on `develop` (decision 9)

With the back-merge and the open cycle arriving by pull request and dev builds committing nothing, no step of the flow writes to `develop` except a merge through its protection, so each repository's `develop` sets `enforce_admins` true once its first back-merge pull request has merged. The owner, as administrator, is bound too. The condition is what proves the flow in that repository before the bypass goes; a repository that makes no release is bound from its switch, since nothing there ever pushes to `develop`. Binding changes nothing in the flow and makes `develop`'s checks a gate for every write, including a mistaken one; an emergency write then needs the setting switched off, which is an explicit change to the repository's settings rather than a routine consequence of the flow. Revised on 2026-09-27: administrators are bound at once wherever `develop` is protected ([below](#2026-09-27-the-rollout-and-administrators-bound-at-once)).

Set aside: leaving the bypass in place on the ground that the flow no longer needs it, which would leave every bypass notice indistinguishable from the routine ones that raised the question in the first place.

### The position this revises

[`releases.md`](releases.md) had recorded, since the handbook's first commit of 14 June 2026, that "the cascade is manual on purpose (a small number of commands at a moment the user is already at the keyboard; an auto-PR version was considered and declined)". No reason for the decline was kept, so it cannot be answered on its own terms. This ruling revises the position rather than reversing it: the back-merge is still a step the releaser runs at the keyboard by one command at the same moment, so the recorded reason still holds and is kept, and it is not an automatic pull request opened by a trigger. What the decline did not weigh is the reason for the change: that the direct push bypasses `develop`'s protection at every release, that the version guard never examines the back-merge, and that 23 of the last 31 back-merges departed from the documented `--no-ff` with nothing reporting it.

Three further statements changed with it. Squash-only settings were given as the reason for a local promotion, which no longer holds; the promotion keeps the reasons that do, namely that `main` carries no required checks for a promotion pull request to wait for, that such a pull request would add a second wait to every release, and that the release ask is the explicit hand it needs. The administrators' bypass was prescribed for the back-merge and the promotion, which the back-merge no longer needs and the promotion never did, since it pushes `main`. And the open cycle was described as a direct push "exempt from `version-guard.yml`, like the back-merge itself"; it is now the verified second commit of the back-merge pull request.

## 2026-09-26: the command as built

Three points the design left inconsistent were settled when the command was built, each following from the design and changing no ruling.

`git back-merge` takes an existing pull request's head as current only if `back-merge-check` passes on it, and otherwise rebuilds the branch. As the design had it, a head that already contained `develop`'s tip went straight to the checks, which is wrong after someone has pressed GitHub's "Update branch": that head carries a second merge commit, the check refuses it, and the command would have stopped on a failing guard although the pull request's own body promises that a second run refreshes it.

`git back-merge`'s refusal in a repository that has not switched finds the transition section of the released `docs/releases.md` by its exact heading, "Until a repository has switched", and quotes it; until that section was released it quoted the "After the release" section instead, and only while that section still gave the direct back-merge. The heading is therefore a contract between the two repositories, and renaming the section degrades the refusal: the command still exits with status 1 and prints the file's path and its address on GitHub, but no longer quotes the section.

`git dev-release` refuses a committing dev build, not only `--open`, once a repository allows merge commits. The design kept the old behaviour wherever the workflow had no `kind` input, but after the switch that behaviour would push to `develop`, which then takes no direct push (decision 9). On 2026-09-27 `--open` gained one case there, its `--direct` flag, for the exception's direct back-merge (below).

Two rulings of the same day bear on the command as built. The first is on how the version line is read. `back-merge-check` then read the version as the version guard did, from the first version line, but admitted an open-cycle commit only where each line it changed was the project's own version: the `version` of the `[project]` table in `pyproject.toml`, and the top-level `version` of `package.json`. The guard's ordinary mode then read the first line of `pyproject.toml` that begins `version =` and the first line of `package.json` that contains `"version"`, wherever each lay. The stricter rule, chosen whilst the findings of the command's review were fixed, admitted no change to any other version line, a dependency's included. Ruled when that choice was reviewed: it stands as built, and the guard is to be aligned with it in a later handbook change, so that the two read the same line again. The alignment was made the next day, in this build, and dev-tools v1.5.0 parses the project's own version too, in `back-merge-check` and `_sot.sh` (2026-09-27, below).

The second is the order of a switch: a repository's switch pull request, which brings the guard with its back-merge mode, merges first, and the call that allows merge commits and disables squash merging is made only once that merge has landed, so that the new guard is on `develop` before any merge commit can be made. That order is what makes `git back-merge`'s single test match the definition of a switch in [`releases.md`](releases.md#until-a-repository-has-switched): the command reads only whether the repository allows merge commits, and a repository that does already carries the guard's back-merge mode.

## 2026-09-26: the repositories the rule reaches

The thirteen repositories that run the version guard switch one at a time, in an order the build plan set and this record does not keep, each only once its release notes come from the shared changelog generator, since the notes would otherwise list every branch commit. Four repositories outside that set were ruled on the same day.

`vos-gspheres`, a private repository of the `garycoding` account that follows the handbook by adoption, comes under this rule: merge commits as its only merge method, `develop` and `main` protected, and its administrators bound at its switch rather than at a first back-merge, since under the policy of 2026-07-04 for that repository (exploratory, no releases) nothing ever pushes to `develop` there. Its release apparatus stays dormant. `yucca-basing`, a Rust exploration begun before PensaForma was chosen as the first Rust desktop application and very probably no longer needed, is left as it is on squash merging; the removal of the transition section does not wait for it. `hazel-tracking`, created on 18 September 2026 and not yet built when this was ruled, meets the rule when it is built rather than by a switch pull request, starting with merge commits and the checked back-merge, if the handbook release that carries the rule has come out by then; otherwise it switches with the others. `pvl-dotview` comes under the rule directly when it is aligned with the handbook, without first being restricted to squash merging: it writes no release notes for a generator to spoil and it already merges with merge commits, so restricting it first would be undone one release later.

`pensa-forma` switches with its first release rather than with the other code repositories, because its version will live in `Cargo.toml`, its `develop` having no version file yet. The version guard reads `Cargo.toml`, but `back-merge-check` and dev-tools' `_sot.sh`, from which `git back-merge` reads the version and writes the open cycle, do not, and its first release needs that reading in any case.

## 2026-09-26: the trial on GitHub

The design ruled on 2026-09-18 was tried on GitHub before the handbook and the code repositories switched to it, in a scratch repository, ParkviewLab/back-merge-trial, whose `develop` was protected as the strict repositories protect theirs and whose release workflows were assembled from this change's parts with their publishing steps removed. Its seven cases, in order: a branch cut before the release; the release and its back-merge pull request, the command stopped once the pull request was open; a feature merge, then GitHub's "Update branch" on that pull request, which the guard refuses; `git back-merge` run again whilst `develop` moved; a pull request from the branch cut before the release; a dev build that commits nothing; and a direct push refused once administrators are bound. A run was accepted only when a fresh verifier found every recorded outcome, each with its evidence, equal to the expected one. The trial is recorded in the Library, in the book "The back-merge trial", which is this file's standing reference for it.

The first run, with dev-tools v1.4.0, from 04:37 to 05:00 UTC on the 27th, the evening of 2026-09-26 in Los Angeles, was not accepted, on two matters. In the fourth case the command reached the expected outcome, a rebuild from the new `develop` and the merge of the rebuilt head, by its own check that `develop` is an ancestor of the head, not by GitHub's refusal of an out-of-date merge, which the plan had named; the case was restated to what the design requires (the next entry). And `git back-merge`'s last step, which fast-forwards the local `develop` worktree, failed in the handbook's layout, though not fatally: listed from a linked worktree, the bare clone, whose HEAD was `develop`, matched its lookup as well. Ruled 2026-09-26: the `develop` worktree is the first entry on `develop` that has a work tree, and a status that cannot be read stops the pull. The fix was released as dev-tools v1.4.1, and the repeat, from 06:27 to 06:49 UTC with v1.4.1, ran the seven cases again, the fourth as restated, and was accepted.

On 2026-09-27, from 13:45 to 14:01 UTC, with dev-tools v1.5.0, two further cases were accepted: an eighth, a hotfix picked onto `main`, released as v0.1.2 and brought back through the checked pull request ([below](#2026-09-27-a-release-picked-onto-main-and-its-back-merge)), and the sixth again, for the dev image's version label, which the repeat's verifier had found reading "dev" and which the dev docker part's corrected tag order now sets to the dev version. ## 2026-09-26: a head that `develop` has moved beyond

Ruled 2026-09-26, restating what the design requires rather than changing it: a head that `develop` has moved beyond is never merged, and `git back-merge` rebuilds the branch from the new `develop`, whichever check stops it. Where the repository requires branches to be up to date there are two, and the trial's fourth case, as the build plan first wrote it, named only the second: the command's own test, before it asks for the merge, that `origin/develop` is an ancestor of the head, and GitHub's refusal of an out-of-date merge if it does ask. The command tries three rebuilds and then leaves the pull request open. Where a repository does not require up-to-date branches there is nothing to rebuild for: GitHub's merge carries the newer `develop`, and what the back-merge brings is still exactly what the check examined.

Set aside: test-only code in the released script, to suppress its own check so that GitHub's refusal could be exercised deliberately. A released command would then carry a path that exists for its test, and GitHub's refusal is covered by `dev-tools`' own tests, where the fake GitHub answers as GitHub does.

## 2026-09-27: a release picked onto `main`, and its back-merge

The rule for a hotfix, which picks a merged pull request whole onto `main` with `git cherry-pick -m 1` and releases it from there ([`releases.md`](releases.md#picking-a-merged-pull-request-onto-the-release-line)), was written with the rest of this change. The currency check of the handbook branch found, before its pull request opened, that `git back-merge` as then released, dev-tools v1.4.1, could not bring such a release back into `develop`; its simulations of a hotfix in a code repository and in a `VERSION.txt` repository, confirmed by a reading of the command, showed three causes. The command took the newest merge on the tag's first-parent line for the release's promotion, which for a picked release is the previous release's, so it compared the wrong versions and prescribed a wrong repair, the restoration of `develop` to the previous release's placeholder; in a `VERSION.txt` repository, whose merge was in fact clean, it refused and prescribed an older version. In a code repository the merge of `main` into `develop` conflicts on the project's version lines by construction, since after their merge base `main` has moved them to the hotfix's version and `develop` to its placeholder. And `back-merge-check` refused every merge that was not the clean automatic merge of its parents, so no merge resolved by hand could pass the checked pull request.

Three courses were put: to document the hotfix's back-merge as an exception, the direct back-merge with administrators unbound for its one push; to extend `git back-merge` and `back-merge-check` so that a picked release comes back through the checked pull request like any other; and to hold the pick rule back from this change, leaving a hotfix meanwhile with no documented way back into `develop`. The recommendation, the first now and the second in a later dev-tools release, was not taken. Ruled 2026-09-27: the first and the second both, in this build and with nothing deferred, because the build exists to fix how merges and releases are made in every repository, and a follow-up left for a later release would put off what it was undertaken to accomplish. The same ruling is the direction under which the next entry's alignment was made: what the build's reviews find is fixed within the build.

The second course is dev-tools v1.5.0. A release counts as picked onto `main` when the stretch of `main`'s first-parent line that its back-merge brings holds no promotion, that is, no merge whose second parent `develop` holds. For such a release `back-merge-check` accepts, where the plain automatic merge conflicts, the automatic merge in which the project's own version lines of `develop` and of the merge base are first set to `main`'s released version, and `git back-merge` makes the merge from the tree the check computes for it, so that the two apply one rule, then adds the open-cycle commit as for any release. A `VERSION.txt` repository needs no such merge, since only `main` has changed its version since the merge base; there only the command's search for the promotion had to be corrected.

The exception was assigned the same day to a hotfix whose merge conflicts outside the version lines. As first built, `git back-merge` answered such a hotfix with decision 6's repair (d) ([above](#a-conflicting-back-merge-decision-6)), the pull request bringing `develop`'s side of each conflicting passage into agreement with `main`'s. For a hotfix that pull request would undo newer work: the conflict arises where `develop` has changed the picked lines again since the pull request merged, and `main`'s side of it is the picked change, the older. Ruled 2026-09-27: the command prescribes the exception instead, the direct back-merge with administrators unbound for its one push, the conflict resolved by hand.

The command's review, by one independent reviewer, found three ways in which a version change made by hand on `develop` could pass a hotfix's back-merge without the refusal that prescribes decision 6 (a), none of them reachable within the handbook's flow: a promotion whose back-merge had not landed, followed by a pick; a head built by hand whose merge had a stale first parent; and a first release that `main` reached by a fast-forward, which counts as picked. It found as well a false refusal present since the command's first release, v1.4.0: for a first release reached by a fast-forward, the command took a pull request's merge, which `develop` already held, for the release's promotion, and refused a clean back-merge with a wrong repair. Two fixes were put, both recommended. Fix A sought the promotion only on the stretch of the tag's first-parent line that `develop`'s tip does not hold, rather than as far as the previous release's tag, and took `develop`'s tip rather than the merge's own first parent for `develop`'s side in the check, which closed the first two ways and the false refusal. Fix B let a hotfix's merge take from `main` only the version change the release flow itself makes, a single merge base at a release R and `develop` at R's next-patch placeholder, which R's back-merge opened, and refused any other version on either side, which closed all three. Ruled 2026-09-27: both.

The fixes left the two scripts apart on one point, where `develop` and `main` have more than one merge base. `git back-merge` refused every such release, naming the direct back-merge, whereas `back-merge-check` refuses there only a picked release or a version mismatch, and passes a release made by promotion whose merge is clean. Ruled 2026-09-27: the command refuses only where the check does, so that the two apply one rule, and names the exception for each refusal. That includes a promotion whose versions disagree: the promotion it compares may then be an earlier release's, made from a `develop` that did not yet hold the back-merge that has since moved its version, and restoring `develop`'s version would be the wrong repair. The reasons: the checked pull request is not to be bypassed where the check can verify the merge; more than one merge base harms only a hotfix's rewrite of the version lines and the command's comparison of versions; and git's merge handles several merge bases, with the check confirming the result. Set aside: refusing every such release.

Fix B's own refusals, where `develop`'s version is not the placeholder the release flow sets or the merge base's version is not a release, needed a repair to name. Ruled 2026-09-27: decision 6 (a)'s, one reviewed commit restoring `develop`'s version lines to the version the refusal names, pushed directly, then `git back-merge` again. The reasons: that is the fault decision 6 (a) was written for, a version change on `develop` outside the flow; its direct push carries only the version lines, and the checked pull request then examines everything else; and the direct back-merge stays for the conflicts that only a person can resolve. Set aside: naming the direct back-merge for these as well.

The exception's own procedure lacked one step, found whilst the handbook's description of it was written. In a code repository its merge conflicts on the version lines as well, and once they are resolved to `main`'s release version, `develop` has to be left at the next placeholder. The handbook forbids typing a version by hand, and `git dev-release --open`, the command that writes the placeholder, refused in every repository that had switched, since `develop` there takes no direct push. Two courses were put: a flag to `git dev-release --open` in v1.5.0, with which, once the merge has been committed by hand, the command writes the placeholder, commits it and pushes both commits in the one push the exception already makes; or the placeholder given by the handbook and set by hand with `uv` or `npm`, which would have been the one place in the flow where a person writes a version, against the handbook's own rule. Ruled 2026-09-27, as recommended: the flag, `--direct`, accepted only with `--open`, so that versions stay written by the tool. Without it, `--open` still refuses in a repository that has switched. Set aside: the placeholder set by hand.

One question remained: how a hotfix meets what the release preflight requires. It is released from `main`, which holds only the last release and what is picked onto it, so a fix made on `develop` does not reach it. Three courses were put: to pick a lagging pin's pull request onto `main` with the hotfix and let stale documents wait for the next promotion; to pick both; to pick neither. Ruled 2026-09-27, as recommended: the first. A pin below its floor is moved by its pull request into `develop`, and that pull request is also picked onto `main` with `git cherry-pick -m 1` before the hotfix's bump, so that the hotfix's own release, which runs the workflows as `main` holds them, runs the pinned script at or above its floor, a floor being there to avoid running a script with a known defect. A stale document the currency check finds is fixed on `develop` and reaches `main` at the next promotion, since the hotfix republishes the documents the last release already published. Set aside: picking the documents' fixes as well, and picking neither.

## 2026-09-27: the version guard aligned with the check

The alignment that the ruling of 2026-09-26 had left to a later handbook change was made within the build and kept in it on a ruling of the same day. It was made under the direction ruled earlier that day, that what the build's reviews find is fixed within the build rather than recorded for a later release (above). The guard's ordinary mode now compares the project's own version with the base's: `[project].version` in `pyproject.toml` and the top-level `version` in `package.json`, as `back-merge-check` reads them; in `Cargo.toml`, which `back-merge-check` does not read, `[package].version`, or `[workspace.package].version` where the crate inherits it or the manifest is a workspace's; and `VERSION.txt` whole, as before. It parses the TOML files with Python's `tomllib` and `package.json` with `jq`.

The first-line reading it replaces could be misled in both directions. A version line of another table placed before the project's (a tool's table, a dependency's, a nested `"version"` in `package.json`) made a pull request that changed only that line fail, and made one that changed the project's version pass; and a version line reformatted without a change of version failed. Run on 29 constructed pull requests before the change was committed, under bash 3.2 and under bash 5.2, the old reading gave the wrong outcome in 10 and the new one in none.

Two behaviours were settled with it. A file that holds no static version either in the pull request or at the base, as a `pyproject.toml` whose version is dynamic, has nothing to guard and passes, whilst a version that appears or disappears between the two is a change and fails, as it did before. And a version file that cannot be parsed fails with the parser's error, where the first-line reading, which never parsed the file, passed it.

From v1.5.0 `dev-tools` reads the version the same way, as ruled the same day: `back-merge-check`, and `_sot.sh` where it reads the version at a commit, as `git back-merge` does, parse the version file for the project's own version, where they had taken its first version line, so that one reading holds in the guard and in the tools. Set aside: keeping the first-line reading and correcting only the comments that described it.

## 2026-09-27: the rollout, and administrators bound at once

The change reached every repository the rule covers but three in one build, from 20:29 UTC on 2026-09-26 to 23:29 UTC on 2026-09-27, 27 hours of wall-clock time, most of it spent waiting on reviews, CI and the owner's rulings. `dev-tools` carried the command and the check from the start of the build to v1.4.0 at 03:51 UTC on the 27th, the evening of 2026-09-26 in Los Angeles; the trial ran from 04:37 to 06:49 and again, with v1.5.0, from 13:45 to 14:01 (above). The handbook pull request that brought this record, #54, opened at 17:20 UTC on the 27th and was merged by the owner at 17:22, before the pilot rather than after it as the build had planned, and the handbook's merge settings followed that merge. The pilot, paper-boxing, switched at 17:50, merged two pull requests of its own with merge commits, released v0.4.2 at 19:04 and brought it back through the checked pull request at 19:05; one verifier found the switch made before the settings changed, both pull requests merged with merge commits, and the release's back-merge pull request labelled, checked and merged, with no direct push to `develop`. The handbook released v1.0.0 at 20:47, its back-merge pull request merging 45 seconds later; `dev-tools` switched at 21:02 and released v1.5.1 at 21:54, in which `git back-merge`'s refusals cite this handbook's sections in place of the design's decisions. The nine other code repositories switched at about 22:58, each switch pull request merging before its merge settings changed, and each then released a patch whose back-merge came through the checked pull request, from 23:04 to 23:29. A verifier found, for each of those releases, the back-merge pull request labelled and merged, its merge commit's second parent the head on which the required checks passed, the tag an ancestor of `develop`, `develop` at the next placeholder, and no direct push to `develop` over the release. The two websites, parkviewlab.ai and zoestum.ai, re-synced their pointer files, and `vos-gspheres` switched and was bound, as ruled on 2026-09-26. Three repositories remain: `pensa-forma`, which switches with its first release; `hazel-tracking`, which meets the rule when it is built; and `pvl-dotview`, which comes under it when it is aligned with the handbook, its `develop` already protected and bound (below).

Decision 9's condition, a repository's first back-merge pull request, was not waited for. At 21:19 UTC a coding agent, briefed to work on a branch, pushed a commit to `dev-tools`' `develop` directly; `develop` was not yet bound there, and the push landed before any check ran: `reuse` and `test` ran on it afterwards, and the version guard, which runs only on pull requests, not at all. An agent's commands run with the owner's credentials, so the administrators' bypass is also every agent's. The commit was reverted by a pull request, and its change returned by another. Ruled 2026-09-27, the same day: administrators bound on `develop` at once in every repository whose `develop` is protected, switched or not; `pvl-dotview`'s `develop` protected with its own checks and bound; and a new repository's administrators bound as soon as its `develop` is protected. The cost falls on a repository that has not yet switched: its release still ends with the direct back-merge and a direct push that opens the next cycle, and a dev build whose workflow lacks the `kind` input pushes to `develop` too; `enforce_admins` is now switched off for those pushes and on again after them, each switch with the owner's go-ahead, as [`releases.md`](releases.md#until-a-repository-has-switched) gives it. Set aside: waiting for each repository's first back-merge pull request, which would have left the bypass open to any agent's mistaken push until then.

The templates' two pins and the handbook's own guard pin moved to v1.5.1 with this entry.
