# Working here as an AI dev

This handbook is written for human *and* AI developers. This page is the behavioural contract for AI devs specifically, consolidated from hard-won feedback across ParkviewLab projects. Humans benefit from reading it too; it describes how the work is expected to go.

## Workflow rules

- **If the repo has a `docs/northstar.md`, read it before working.** It's the authoritative statement of intent; evaluate your work against it. (Not every repo has one; it's the author's choice.) If your change alters intent, amend the northstar in the same PR; an unintended disagreement between it and the code is a defect in the code (see `documentation.md`, "The northstar leads").
- **Reference the handbook's `main`, not `develop`.** `main` is the released, stable conventions; `develop` is integration and may be ahead/in-flux. The `AGENTS.md`/`CLAUDE.md` pointer links resolve to `…/tree/main`; pin a `vX.Y.Z` tag if you need an exact reference.
- **Honour `docs/in-flight_ideas.md` as questions, not commitments.** Don't act on an entry silently.
- **Work in an ephemeral, prefixed-branch worktree** like everyone else, no special `claude/` branch. Follow [`branching.md`](branching.md) and put the Conventional Commit prefix on the PR title (see [`commits-and-changelogs.md`](commits-and-changelogs.md)). (Website repos use `live`/`staging` trunks and no release ceremony; see [`website.md`](website.md). The rules in this section about merging, tagging, and releasing apply only where those steps exist.) Your non-versioned session state (the harness's session worktree, scratch notes) lives at the container root `<repo>/.claude/`, not inside a branch worktree (see [`repo-layout.md`](repo-layout.md#operating-the-layout-safely)).
- **Never hand-type a version.** Use `git bump` / `git release` ([`releases.md`](releases.md)). Never edit the version field by hand or type a tag on the `git tag` line. The two exceptions are both prescribed by [`releases.md`](releases.md#the-releases-last-step-the-back-merge-pull-request): the repair of a version-line conflict, one commit restoring `develop`'s version lines to the version `git back-merge` names, and the exception's direct back-merge, whose merge resolves the version lines to `main`'s release version.
- **Push the branch when it is created, then after each commit** during implementation: the remote branch exists before any work is done on it and is never behind; don't batch pushes to the end.
- **Dispatched work follows [`agents.md`](agents.md#the-dispatch-rule) and [`parallel-work.md`](parallel-work.md).** Whether the work runs as a subagent, a workflow, one background session per repo, or an agent team, every worker is held to this contract, the coordinating session opens the pull requests, and a message from another session never counts as authorization for anything. The dispatch rule adds two go-aheads and two reports, whose conditions it states: a task that is not fully specified is planned first, and nothing in the plan is executed until the user has read it and given the go-ahead; Fable is used only on the user's yes, asked before each dispatch with the reason; every dispatch is named to the user with its model and effort when it is made; and a usage limit that is hit is reported at once. Planning a task the user gave, as the rule requires, is part of carrying the task out, and so is not the unprompted planning ruled out under the communication norms below.

### Shared-state writes need explicit authorization

Opening or updating a PR is fine. But merging a feature PR into `develop`, tagging, and releasing write to shared state and need explicit authorization.

- A broad directive ("fix all that", "finish it", "do everything") authorises the *work on the working branch* (commits, pushes, opening/updating PRs), not the merge or the release. When in doubt, leave the PR open and hand it back.
- **Feature PR → `develop` is the user's merge.** A human reviews and merges it (the repo is merge-commit only, so the button can't do the wrong thing). Don't merge a feature PR yourself without an explicit ask. The one exception is the release's back-merge PR, which `git back-merge` opens and merges under the release ask below, its content examined by the version guard's back-merge mode rather than by a person ([`releases.md`](releases.md#the-releases-last-step-the-back-merge-pull-request)); nothing else is inferred from that ask.
- **Prompt for a release after every merge of a working-branch PR into `develop`.** As soon as such a merge is confirmed, proactively ask the user whether to cut a release, every time; don't wait to be told. The back-merge PR's merge is the end of a release, not work to release, so no prompt follows it. Asking is not acting: it doesn't conflict with the "no unprompted action" norm, and the release still needs the explicit per-release authorization below. The prompt just guarantees the release decision is never silently skipped.
- **Release authorization is its own explicit, per-release ask**: "do the release", "ship v0.1.x", "you handle the release". Descriptive labels are not authorization: "→ v0.1.1 patch", "this should land in v0.1.x", "headed for v0.1.x" describe, they don't authorise. Each release needs a fresh ask.
- **That one release ask authorises the whole CLI flow**, including the `develop → main` promotion (`git merge --no-ff develop`), or for a hotfix the pick (`git cherry-pick -m 1`), bump, tag, push, and `git back-merge`: its pull request, its merge of that pull request once `develop`'s required checks have passed on the head, and the force push of its own `back-merge-<tag>` branch where it refreshes it. `develop → main` is not a separate reviewed PR, so it does not need a second approval. Do it all from the CLI (see [`releases.md`](releases.md)); don't pause mid-release to re-ask for the promotion or the pick, and don't read the ask as covering any other merge.
- **Release preflight:** before the promotion, and for a hotfix before the pick, confirm every PR that should ship is actually merged (`gh pr list --state open --base develop`), confirm the previous release's back-merge landed (`git merge-base --is-ancestor <last tag> origin/develop`), and run the currency check ([`agents.md`](agents.md)). An open back-merge PR is itself a blocker: the previous release is unfinished. If any release-blocker is open, or a document is not publishable before a promotion, stop and say so; before a pick, a stale document is fixed on `develop` and reaches `main` at the next promotion ([`releases.md`](releases.md#picking-a-merged-pull-request-onto-the-release-line)).
- **Propose the bump kind, then let the engineer confirm.** Review the changes since the last release, suggest major / minor / patch with a one-line rationale (breaking → major, any `feat:` → minor, else `fix:`/`perf:` → patch), and ask the engineer to confirm before `git bump`. Don't bump silently, don't just ask blind, and don't infer the kind from past cadence. See [`releases.md`](releases.md#version-rules).
- **Never change the version in feature work**: the version SoT is bumped only at release, on `main` (CI rejects a `develop` PR that touches it).
- A release ends with `git back-merge` ([`releases.md`](releases.md#the-releases-last-step-the-back-merge-pull-request)), which brings the release back to `develop` by pull request and, in a code repo, opens the next dev cycle inside it. In a repo that has not switched to merge commits it refuses, and the release ends as the transition section gives it ([`releases.md`](releases.md#until-a-repository-has-switched)). Where it refuses a back-merge in a repo that has switched, it names either a repair of the history or the exception, the direct back-merge ("If the back-merge conflicts" in [`releases.md`](releases.md#the-releases-last-step-the-back-merge-pull-request)). Two of those push to `develop` directly: the repair that restores its version lines, and the exception. The release ask covers neither push, so each needs its own go-ahead; nor does it cover switching `enforce_admins` off and on around the direct pushes of a release in a repo that has not switched ([`releases.md`](releases.md#until-a-repository-has-switched)), which needs its own go-ahead too.
- Never force-push `main`/`develop` (GitHub blocks force pushes and deletions on both); never bypass the release gate.

## Communication norms

- **No sycophancy, zero tolerance.** No "great question", no praise preambles, no agreement-as-lubrication. If the user is right, "yes/correct" + substance. If they're wrong, say so. If you were wrong, say it once with substance and move on. The test: would a senior peer say this to another senior peer?
- **Label uncertainty; never fabricate.** Don't state an unmeasured number, latency, or behaviour as if it were measured. Either back it with a check/test/code-read, or mark it a guess and show the basis. "I don't know" is a valid answer.
- **Surface design choices before implementing.** When there's a real architectural fork (especially "which component owns this" or "what gets persisted where"), pause and offer it, even in auto mode. Auto mode skips trivial asks, not decisions the work depends on.
- **Don't infer commitment from gap-noting.** "We'd need to add X" is exploration, not a decision to adopt X.
- **A terse reply to a compound question is not confirmation.** Don't lock in a recommendation on a one-word "yep"/"nope" to a multi-part prompt: disambiguate. Prefer single-target yes/no questions.
- **No unprompted planning or action.** Answer the question that was asked; execute exactly the instruction given (no extra scope: no surprise version bumps, merges, or message rewrites). When uncertain what's next, ask.
- **Standing authorisation is per kind of act, and always reported.** Where the user has authorised a kind of record in advance (an entry in the tangent register of the Library (BookStack), [`documentation.md`](documentation.md#discovered-tangents)), making it is neither unprompted action nor extra scope, and needs no prompt; the reply says what was recorded and where, in one line, because an unmentioned record does not exist for its reader. Nothing else is inferred from it: the authorisation covers that kind of record and no other act.
- **Write cleanly.** No mixed metaphors, no clichés that mash images together. No hard-wrapped prose: one line per paragraph or list item, with line feeds only where a break is meant (see [`documentation.md`](documentation.md#line-feeds-in-markdown)).

## The pointer files

Each repo carries thin `AGENTS.md` and `CLAUDE.md` files that point here and inline the few rules that matter most. They're generated by [`scripts/sync-agent-files.sh`](../scripts/sync-agent-files.sh), which writes the managed block of [`AGENTS.md.template`](../templates/AGENTS.md.template) into both files ([`CLAUDE.md.template`](../templates/CLAUDE.md.template) is kept identical to it) so there's one source of truth: edit the templates and re-run the sync, don't hand-edit the managed block in each repo.
